# SPEC-005: CLI

Status: **Implemented** · Task: T6 · Crate: `pressa-tui`
· ADRs: [0006](../docs/adr/0006-workspace-of-four-crates.md),
[0008](../docs/adr/0008-tracing-to-a-log-file.md),
[0010](../docs/adr/0010-test-only-dependencies-need-an-adr.md)

## Problem

Everything below `pressa-tui` exists and is tested — schema loading (T2),
validation (T3), the repository (T4), the services (T5) — but nothing can be
run. `main.rs` today initialises logging against the working directory, logs one
line and exits; it does not parse arguments, does not discover a project, and
never constructs a repository or a service. There is no way for a user, or for
the Golden Path test, to reach any of that code.

There is also no entry point for a *new* project. `discover_project` needs a
`pressa.yaml` to find, and nothing writes one, so the first-run experience is
"read the docs and hand-write YAML".

## Goal

`pressa` becomes a real binary: three subcommands parsed with `clap`, a project
resolved either by walking up from the working directory or from `--project`,
tracing configured at the level `--log-level` asks for, and errors that happen
before the TUI owns the screen printed plainly to stderr with exit 1. `init`
scaffolds a project that `validate` accepts; `validate` reports a schema as
either one summary line on stdout with exit 0, or the YAML path of the problem
on stderr with exit 1; `dev` performs the whole startup sequence — project,
logging, database, migrations, services — and then stops at the edge of the
screen, which belongs to T7.

## Non-goals

This task builds the *entry point*, not the application behind it. A reader may
reasonably expect the following here and will not get it:

| Not here | Where it lives instead |
|---|---|
| The screen. `TerminalGuard`, raw mode, the alternate screen, layout, `AppState`, `update()`, the event loop. `dev` in T6 does every startup step and then refuses to draw | [006](006-tui-shell.md), T7 |
| The keymap, the hint bar, `q`/`Ctrl+C` handling | [006](006-tui-shell.md), T7 |
| Writing the `collections` config snapshot on startup ([`storage.md`](../docs/storage.md) §2). The migration creates the table and nothing fills it; the coordinator assigned this to T7, where "application start" becomes real | [006](006-tui-shell.md), T7 |
| Schema diffing, migration of user data, `pressa generate` | M3, [roadmap](../docs/roadmap.md) §1 |
| Any subcommand beyond `init`, `dev`, `validate` — no `pressa list`, `pressa import`, `pressa export`, `pressa new`. A headless CRUD CLI is a second UI over the same services and would need its own spec | M1 (import/export), otherwise unproposed |
| Shell completions, man pages, `--version` beyond clap's built-in | not in M0 |
| Configuration outside `pressa.yaml`: no env vars, no `~/.config/pressa`, no `PRESSA_*` overrides | [001](001-schema-config.md) "Non-goals" |
| Log rotation, `--log-file`, logging to stderr, filtering by target or span | [ADR-0008](../docs/adr/0008-tracing-to-a-log-file.md) "Revisit when" |
| `--project` pointing at a `pressa.yaml` file rather than at its directory | `project_at` takes a directory ([001](001-schema-config.md)) |
| Colourised or otherwise styled CLI output. Errors are plain text, so they stay readable when piped | [`tui.md`](../docs/tui.md) §6 limits colour to the rendered TUI |
| `anyhow`. `AGENTS.md` permits it in `main.rs`, but it is absent from `pressa-tui`'s dependency table in [`architecture.md`](../docs/architecture.md) §2 and from `Cargo.lock`, and an `ExitCode` shim needs no error-reporting crate | not added |

## User stories

- As a new user, I want `pressa init` to leave me a working project I can
  immediately validate, so that my first run is not a YAML-writing exercise.
- As a user editing `pressa.yaml`, I want `pressa validate` to tell me the
  path of what I broke and exit non-zero, so that I can put it in a pre-commit
  hook and read the answer without opening the TUI.
- As a user working in a subdirectory of my project, I want `pressa` to find
  the project above me the way `git` does, so that I do not have to `cd` first.
- As a user with several projects, I want `--project <dir>` to say exactly
  which one I mean, so that discovery cannot pick the wrong one.
- As a developer debugging a startup failure, I want the reason on stderr and a
  non-zero exit code, so that I am not left with an empty screen and no clue.

## UX

A CLI's screens are its terminal transcripts. `$` is the prompt, `#` a comment,
and `→ exit N` the process exit code — none of the three is printed by pressa.

### A — `pressa --help`

```text
$ pressa --help
A terminal-native, schema-driven data manager

Usage: pressa [OPTIONS] [COMMAND]

Commands:
  dev       Open the TUI for this project [default]
  init      Scaffold pressa.yaml and .pressa/ in this directory
  validate  Load and check the schema, then report
  help      Print this message or the help of the given subcommand(s)

Options:
      --project <DIR>    Use this project directory instead of searching upward
      --log-level <LVL>  [default: info] [possible values: trace, debug, info, warn, error]
  -h, --help             Print help
  -V, --version          Print version
→ exit 0
```

### B — `pressa init` in an empty directory

```text
$ pressa init
created pressa.yaml
created .pressa/
run `pressa` to open it
→ exit 0
```

Afterwards the directory is:

```text
.
├── pressa.yaml          # a byte-for-byte copy of examples/blog/pressa.yaml
└── .pressa/
    └── pressa.log       # created by logging::init, one line in it
```

`data.db` is **not** here: the database file is created lazily, by
`SqliteRepository::open` on the first `dev`. `init` never links the storage
crate into its own path.

### C — `pressa init --project ./blog`

```text
$ pressa init --project ./blog
created blog/pressa.yaml
created blog/.pressa/
run `pressa --project blog` to open it
→ exit 0
```

`--project` names the directory to scaffold *into*, and `init` creates that
directory if it does not exist. It is the one subcommand for which `--project`
does not mean "skip discovery", because `init` does not discover anything.

### D — `pressa init` where `pressa.yaml` already exists

```text
$ pressa init
pressa: pressa.yaml already exists in /home/u/blog
→ exit 1
```

Nothing is written — not the file, not `.pressa/`, not the log. The refusal is
decided before anything is created, which is also why this is the one command
that can fail without leaving a log entry behind.

### E — `pressa validate` on a good schema

```text
$ pressa validate
schema ok: 1 collection, 8 fields
→ exit 0
```

The wording is normative: [SPEC-000](000-m0-golden-path.md) step 2 asserts it.
Both nouns are pluralised independently, and `fields` is the total across every
collection:

```text
schema ok: 3 collections, 17 fields
```

### F — `pressa validate` on a schema with an unknown field type

```text
$ pressa validate
pressa: collections.posts.fields[3].type: unknown field type 'relation' (expected one of: text, textarea, number, boolean, datetime, select, json)
→ exit 1
```

The text after `pressa: ` is `ConfigError`'s own `Display`, unaltered — the
YAML path comes from [001](001-schema-config.md) and is not re-worded here.
Loading stops at the first problem, so exactly one line is printed.

### G — `pressa validate` with no project anywhere above

```text
$ pressa validate
pressa: no pressa.yaml found in /tmp/scratch or any parent directory
→ exit 1
```

Nothing is created here either: without a project there is nowhere to put a
log, so `.pressa/` is never scattered into a directory that is not a project.

### H — `pressa validate --project examples/blog`

```text
$ pressa validate --project examples/blog
schema ok: 1 collection, 8 fields
→ exit 0
```

`--project` does not walk up: if `examples/blog/pressa.yaml` is missing, this is
screen G naming `examples/blog`, even when the current directory is inside a
valid project.

### I — `pressa dev` / `pressa`, until T7 lands

> **Superseded by [SPEC-006](006-tui-shell.md) §UX screen I.** T7 replaced the
> stub with the event loop: `pressa dev` on a terminal now opens the screen and
> exits 0, and on a stream it cannot own it prints
> `pressa: the terminal could not be prepared: …` and exits 1.
> `CliError::NotImplementedYet` no longer exists. What follows describes T6.

```text
$ pressa
pressa: the TUI arrives in T7
→ exit 1
```

Everything before that line really happened: the project was resolved, logging
was initialised, `.pressa/data.db` was created and migrated, and both services
were constructed. Only the screen is missing, and the non-zero exit is there so
that nobody — a user, a script, or `just run` — mistakes this for a working
TUI. `.pressa/pressa.log` shows the work:

```text
$ cat .pressa/pressa.log
2026-09-09T11:04:22.518Z  INFO pressa: pressa started version=0.0.0
2026-09-09T11:04:22.521Z  INFO pressa: project resolved root=/home/u/blog
2026-09-09T11:04:22.534Z  INFO pressa: services ready collections=1
2026-09-09T11:04:22.534Z  WARN pressa: the TUI arrives in T7
```

`just run` is therefore red for the duration of T6 and turns green in T7, when
this stub is replaced by the event loop. That is the intended, visible cost of
the choice.

### J — `pressa dev` with a project that will not open

```text
$ pressa dev
pressa: collections.posts.list_columns[0]: unknown field 'titel'
→ exit 1
```

The schema is loaded before the database is opened, so a bad schema leaves no
`data.db` behind.

### K — `pressa --log-level error dev`

> The first line is superseded with screen I above; the log behaviour is not.

```text
$ pressa --log-level error dev
pressa: the TUI arrives in T7
→ exit 1

$ cat .pressa/pressa.log
# empty: every event above is INFO or WARN, and the level filter dropped them
```

## Domain model

No domain types. `pressa-core`, `pressa-storage` and `pressa-app` are unchanged
by this task; everything below is `pressa-tui`'s own.

```rust
// pressa-tui/src/cli.rs

/// The parsed command line. `clap`'s derive API builds this from argv.
#[derive(Debug, clap::Parser)]
#[command(name = "pressa", version, about)]
pub struct Cli {
    /// For `dev` and `validate`: the project directory, instead of searching
    /// upward. For `init`: the directory to scaffold into.
    #[arg(long, global = true, value_name = "DIR")]
    pub project: Option<PathBuf>,

    /// Verbosity of `.pressa/pressa.log`.
    #[arg(long, global = true, value_name = "LVL", default_value = "info")]
    pub log_level: LogLevel,

    /// Absent means `Dev` — `pressa` and `pressa dev` are the same command.
    #[command(subcommand)]
    pub command: Option<Command>,
}

#[derive(Debug, clap::Subcommand)]
pub enum Command {
    /// Open the TUI for this project.
    Dev,
    /// Scaffold pressa.yaml and .pressa/ in this directory.
    Init,
    /// Load and check the schema, then report.
    Validate,
}

/// Mirrors `tracing::Level` so that `clap` can parse it and the CLI does not
/// make a `tracing` type part of its public surface.
#[derive(Debug, Clone, Copy, PartialEq, Eq, clap::ValueEnum)]
pub enum LogLevel { Trace, Debug, Info, Warn, Error }

/// Everything that can go wrong before the TUI owns the screen. Rendered as
/// one line after `pressa: `; `thiserror`, because this is library code.
#[derive(Debug, thiserror::Error)]
pub enum CliError {
    #[error(transparent)]
    Config(#[from] pressa_app::config::ConfigError),
    #[error(transparent)]
    Log(#[from] crate::logging::LogError),
    /// Drafted as `Storage(#[from] pressa_core::repository::StorageError)`.
    /// Corrected during T6: `pressa-tui` does not depend on `pressa-core`, so
    /// that type cannot be named here, and adding the edge would need an ADR.
    /// `AppError` is `#[error(transparent)]` over `StorageError`, so the line
    /// the user reads is the storage error's own either way.
    #[error(transparent)]
    App(#[from] pressa_app::AppError),
    #[error("pressa.yaml already exists in {}", .0.display())]
    AlreadyInitialised(PathBuf),
    #[error("could not create {}", path.display())]
    Io { path: PathBuf, #[source] source: std::io::Error },
    /// The T6 stub for a screen T7 owns. Removed when the event loop lands.
    #[error("the TUI arrives in T7")]
    NotImplementedYet,
}
```

## API

```rust
// pressa-tui/src/lib.rs
pub mod cli;
pub mod logging;

// pressa-tui/src/cli.rs
/// Runs the parsed command against `cwd`. Returns the process exit code, so
/// `main` is a shim and every path through the CLI is testable in-process.
pub fn run(cli: Cli, cwd: &Path) -> ExitCode;

/// `pressa init`: scaffold into `dir`, creating `dir` itself if needed.
/// Fails if `dir/pressa.yaml` exists, before writing anything.
pub fn init(dir: &Path, level: LogLevel) -> Result<(), CliError>;

/// `pressa validate`: loads the schema at `paths.config` and returns the
/// summary line for screen E. Printing is the caller's job.
pub fn validate(paths: &ProjectPaths) -> Result<String, CliError>;

/// `pressa dev`: the whole startup sequence, up to the point where T7 takes
/// over. Returns `CliError::NotImplementedYet` on success until then.
pub fn dev(paths: &ProjectPaths) -> Result<(), CliError>;

/// Resolves the project: `project_at` when `--project` was given,
/// `discover_project` from `cwd` otherwise. Not used by `init`.
pub fn resolve_project(project: Option<&Path>, cwd: &Path) -> Result<ProjectPaths, CliError>;
```

```rust
// pressa-tui/src/logging.rs — the T1 signature gains a level.
pub fn init(project_dir: &Path, level: LogLevel) -> Result<(), LogError>;
```

`init`, `validate`, `dev` and `resolve_project` take their directories as
arguments rather than reading `std::env::current_dir()` themselves, so the
tests never change the process's working directory — which is global state
shared by every test thread in a binary.

The scaffolded schema is `include_str!("../../examples/blog/pressa.yaml")`.
That reaches outside the crate directory and ties `pressa-tui`'s build to a
workspace-root path, which is acceptable precisely because the workspace sets
`publish = false`: there is no packaged crate for the path to be missing from.
The benefit is that the file `init` writes and the Golden Path fixture cannot
drift apart, because they are one file.

## Invariants

- Nothing is written to stdout by `dev`, on any path.
- Every non-zero exit prints exactly one line to stderr, beginning `pressa: `,
  and nothing to stdout.
- Exit codes: `0` success, `1` every pressa error, `2` clap's usage errors.
  No other code is produced.
- `init` never overwrites and never deletes a file. If `pressa.yaml` exists,
  the filesystem is untouched.
- A project written by `init` loads: `pressa init` then `pressa validate` in the
  same directory exits 0.
- Logging is initialised only once a directory is known to be a project — after
  `resolve_project` for `dev` and `validate`, after the scaffold for `init`. A
  command that fails to resolve a project creates no `.pressa/`.
- `--log-level` is the subscriber's maximum level; an event above it never
  reaches the file.
- `ProjectPaths` is derived once per process and every path the *subcommands*
  use afterwards comes from it. No `.pressa` or `pressa.yaml` literal appears
  in `cli.rs` outside the `init` scaffold's own messages.
  `logging::init(project_dir, level)` is the stated exception: it keeps the T1
  signature and its own `DATA_DIR`/`LOG_FILE` constants, because `init` starts
  a log for a directory that has only just become a project and for which no
  `ProjectPaths` exists yet. Folding the two sets of constants together is a
  refactor for whoever needs it, not a T6 change.
- Exit codes are `ExitCode` values, never `std::process::exit`, so destructors
  run.

## Error cases

Message shape is `pressa: <message>` on stderr, one line.

| Input | Message | Exit |
|---|---|---|
| `init` where `pressa.yaml` exists | `pressa.yaml already exists in <dir>` | 1 |
| `init` where `.pressa/` exists but `pressa.yaml` does not | — succeeds; `.pressa/` is reused as-is | 0 |
| `init` into an uncreatable or unwritable directory | `could not create <path>` | 1 |
| `validate`/`dev`, no `pressa.yaml` above `cwd` | `no pressa.yaml found in <cwd> or any parent directory` | 1 |
| `validate`/`dev`, `--project X` without `X/pressa.yaml` | `no pressa.yaml found in <X> or any parent directory` | 1 |
| `validate`/`dev`, malformed YAML | `<path>: <serde_yaml message with line and column>` | 1 |
| `validate`/`dev`, schema invalid | `<yaml path>: <problem>`, verbatim from [001](001-schema-config.md) | 1 |
| `dev`, database file unopenable or migration failure | `StorageError`'s own message | 1 |
| ~~`dev`, everything succeeded~~ | ~~`the TUI arrives in T7`~~ — superseded by [006](006-tui-shell.md): success is now the screen, exit 0 | ~~1~~ |
| any command, `--log-level nonsense` | clap's own `invalid value 'nonsense' for '--log-level <LVL>'` | 2 |
| unknown subcommand | clap's own `unrecognized subcommand` | 2 |

Three message shapes are deliberately not ours: clap's usage errors,
`ConfigError`'s wording and `StorageError`'s. Re-wrapping any of them would
mean maintaining a second copy of a message that is already tested elsewhere.

## Acceptance criteria

Parsing

- [ ] `pressa --help` lists exactly three subcommands: `dev`, `init`,
      `validate`.
- [ ] `pressa` with no subcommand parses to the same `Command::Dev` as
      `pressa dev`, asserted on the parsed `Cli`.
- [ ] `--project` and `--log-level` parse both before and after the subcommand
      (`pressa --project X validate` and `pressa validate --project X`).
- [ ] `--log-level` defaults to `Info` when absent and rejects a value outside
      `trace|debug|info|warn|error` with clap's own error and exit 2, without
      loading a schema.

`init`

- [ ] `pressa init` in an empty directory exits 0 and creates `pressa.yaml`
      and `.pressa/`.
- [ ] The file it writes is byte-for-byte equal to `examples/blog/pressa.yaml`.
- [ ] `pressa init` does **not** create `.pressa/data.db`.
- [ ] `pressa init` followed by `pressa validate` in the same directory exits 0
      and prints `schema ok: 1 collection, 8 fields`.
- [ ] `pressa init --project <dir>` scaffolds into `<dir>`, creating `<dir>`
      itself when it does not exist, and leaves the working directory untouched.
- [ ] `pressa init` where `pressa.yaml` exists exits 1, prints
      `pressa: pressa.yaml already exists in <dir>` to stderr, prints nothing to
      stdout, leaves that file byte-for-byte unchanged, and creates neither
      `.pressa/` nor a log file when they were absent.
- [ ] `pressa init` into a directory that already has `.pressa/` but no
      `pressa.yaml` exits 0 and does not disturb `.pressa/`'s contents.

`validate`

- [ ] `pressa validate --project examples/blog` exits 0 and prints exactly
      `schema ok: 1 collection, 8 fields` to stdout.
- [ ] On a two-collection schema the summary pluralises both nouns
      (`schema ok: 2 collections, N fields`) and `N` is the field total across
      collections.
- [ ] `pressa validate` on a schema with `type: relation` exits 1 and prints a
      stderr line containing `collections.posts.fields[3].type`.
- [ ] `pressa validate` with no `pressa.yaml` above the working directory exits
      1, prints a line containing `no pressa.yaml found`, and creates no
      `.pressa/` in that directory.
- [ ] `pressa validate --project <dir>` with no `pressa.yaml` in `<dir>` fails
      naming `<dir>`, even when run from inside a valid project.
- [ ] `pressa validate --project <dir>` from an unrelated working directory
      exits 0 on a valid `<dir>` — discovery is bypassed, not merely preferred.

`dev`

- [x] ~~`pressa dev` on a valid project exits 1 and prints exactly
      `pressa: the TUI arrives in T7` to stderr, and nothing to stdout.~~
      Superseded by [SPEC-006](006-tui-shell.md): the screen replaced the stub.
- [ ] After that run `.pressa/data.db` exists and is a migrated database (a
      `SqliteRepository` opened on it in the test can list a collection).
- [ ] After that run `.pressa/pressa.log` contains a line recording that the
      services were built.
- [ ] `pressa dev` on an invalid schema exits 1 with the `ConfigError` message
      and leaves no `.pressa/data.db`.
- [ ] `pressa` with no subcommand behaves identically to `pressa dev` on the
      same project, end to end.

Logging

- [ ] Each of `init`, `validate` and `dev`, on its success path, leaves a
      non-empty `.pressa/pressa.log` in the project directory.
- [ ] `pressa --log-level error dev` leaves `.pressa/pressa.log` empty while the
      default level leaves it non-empty, on the same project.
- [ ] `logging::init` takes the level as a parameter; no test sets a global.

Cross-cutting

- [ ] Every command that exits non-zero prints exactly one line to stderr, and
      that line starts with `pressa: `.
- [ ] Every command that exits non-zero prints nothing to stdout.
- [ ] No pressa error produces an exit code other than 1.
- [ ] `pressa-tui/Cargo.toml` gains `clap` as its only new runtime dependency
      and `assert_cmd` + `predicates` as its only new dev-dependencies;
      `pressa-core`, `pressa-storage` and `pressa-app` are unchanged, and
      `pressa-tui/tests/architecture.rs` still passes.
- [ ] No `unwrap()`, `expect()` or `panic!()` outside `#[cfg(test)]`.

## Tests

`pressa-tui/tests/cli.rs`, with a `TempTree` helper of the kind already in
`pressa-app/tests/support/mod.rs` — one throwaway directory per test, no shared
working directory. End-to-end cases use `assert_cmd`; everything that can be
checked without a process is a unit test on the function.

| Criteria | Test |
|---|---|
| Parsing: default subcommand, flag positions, `--log-level` default and rejection | unit tests on `Cli::try_parse_from`, no process spawned |
| `init` success, template equality, refusal, `--project` target, `.pressa/` reuse | unit tests on `cli::init` over a `TempTree`; one `assert_cmd` spawn for the refusal's exit code and stderr |
| `validate` wording and pluralisation | unit tests on `cli::validate`, which returns the string |
| `validate` and `dev` exit codes, stdout/stderr split | `assert_cmd` spawns asserting `.failure()` / `.success()` and stream contents |
| `dev` leaves a migrated `data.db` | spawn, then open the file with `SqliteRepository` in the test |
| `resolve_project`: discovery from a nested directory, `--project` bypass | unit tests over a `TempTree` |
| `--log-level` filtering | two spawns on the same project, asserting the log file's size |
| One line on stderr, nothing on stdout, exit 1 | asserted on the captured output of every failing spawn |

`examples/blog/pressa.yaml` is the good-schema fixture, used directly rather
than copied, so the example and the tests cannot drift.

## Open questions

None. The eight questions this spec was drafted with were answered by the
coordinator on 2026-09-09 and are folded in above: lazy `data.db` (Q1); every
pressa error exits 1 (Q2); `dev` performs the full startup sequence and then
fails with `the TUI arrives in T7` (Q3); `--project` is `init`'s target
directory (Q4); the scaffold is `include_str!` on `examples/blog/pressa.yaml`
(Q5); `assert_cmd` and `predicates` are added under ADR-0010 (Q6); all
three subcommands initialise logging, once a project directory is known (Q7);
the `collections` snapshot belongs to T7 (Q8). `anyhow` is not added.

`assert_cmd` and `predicates` are covered by
[ADR-0010](../docs/adr/0010-test-only-dependencies-need-an-adr.md), accepted
2026-09-09; nothing further blocks implementation.
