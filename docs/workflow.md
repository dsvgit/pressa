# Рабочий процесс координатора

Status: Draft · Last updated: 2026-09-06

Этот документ — для человека. [`AGENTS.md`](../AGENTS.md) говорит агенту, что
делать; [`development.md`](development.md) объясняет, почему процесс устроен
именно так. Здесь — что делаете вы: что печатать, что проверять, когда
говорить «стоп».

Документ на русском намеренно: остальные доки в `docs/` читает агент, этот
читаете только вы.

---

## 1. Ваша роль

Вы — единственный координатор. Агент пишет код; вы принимаете три решения на
каждую задачу, и на них держится весь процесс:

| # | Решение | Когда |
|---|---|---|
| 1 | Перевести спеку `Draft → Approved` | до начала кода |
| 2 | Принять снапшоты (`just snap`) | после реализации UI |
| 3 | Смержить PR | после ревью |

Всё остальное агент делает сам. Эти три — нет, и не потому, что он не справится,
а потому что ворота, которые открывает тот же, кто в них входит, — не ворота.
Если спеку одобряет тот же процесс, который её реализует, статус `Approved`
перестаёт что-либо значить.

---

## 2. Разовая настройка

Делается один раз, дальше не вспоминаете.

Сделано, ничего повторять не нужно:

```bash
cargo install just         # 1.58.0 в ~/.cargo/bin
```

В репозитории лежит `.claude/`:

| Файл | Что делает |
|---|---|
| `commands/spec.md` | роль spec-writer: шаблон, вопросы вместо догадок, статус `Draft` |
| `commands/task.md` | роль implementer: ветка, проверка статуса спеки, тесты вперёд, `just ci` |
| `commands/review.md` | роль reviewer: сверка diff'а с критериями по одному |
| `hooks/ci-check.sh` | гоняет `just ci`, когда изменились `.rs` / `Cargo.*` / снапшоты |
| `settings.json` | разрешения на `cargo`, `just`, читающий `git`; подключение хука |

Отдельной роли tester нет: «сначала падающие тесты» — это шаг 2 в `task.md` и
пункт в `AGENTS.md`. ADR закрываются плагином
`mattpocock-skills:domain-modeling`.

Хук молчит, пока нечего проверять: до T1 нет `Cargo.toml`, а при чистом дереве
проверять нечего. При красном `just ci` он не даёт агенту закончить и передаёт
ему вывод — вмешиваться вам не нужно.

## 3. Цикл одной задачи

Одна задача → одна ветка → один PR. Ниже — что вы печатаете, по шагам.

### Шаг 0. Ветка — автоматически

Ничего не печатаете. `/task T4` сам проверяет, что дерево чистое и вы на `main`,
и создаёт `feat/t04-storage-repository` — имя выводится из файла спеки. Если
дерево грязное или вы на чужой ветке, агент останавливается и спрашивает.

Ветка — механика, а не решение: её имя однозначно следует из номера задачи.
Ручными остаются только те шаги, где вы что-то решаете.

### Шаг 1. Спека

Смотрите статус спеки в её шапке.

**Если `Approved`** — пропускаете шаг, идёте на шаг 2.

**Если `Draft`** (сейчас это все спеки) или спеки нет вовсе (009, 010):

```
/spec 006 оболочка TUI
```

Агент дописывает спеку и задаёт вопросы там, где требование неоднозначно.
**Отвечайте, а не отмахивайтесь** — каждый неотвеченный вопрос превращается в
догадку в коде.

Дальше вы читаете спеку целиком и проверяете:

- [ ] секция **Non-goals** заполнена и конкретна — именно она останавливает
      разрастание скоупа во время реализации;
- [ ] **Acceptance criteria** — проверяемые утверждения, а не пожелания.
      «Ошибка называет путь в YAML» — годится. «Хорошая обработка ошибок» — нет;
- [ ] для UI-спеки есть ASCII-макет каждого экрана: агент не видит скриншотов,
      макет — это его единственное описание вёрстки;
- [ ] ничего из списка отложенного ([`roadmap.md`](roadmap.md) §3) не заехало.

Устраивает — правите статус на `Approved` руками. Это ваша подпись.

### Шаг 2. Реализация

```
/task T4
```

Агент читает спеку, её ADR, существующий код, **пишет падающие тесты**, потом
реализует, потом гоняет `just ci`.

Пока он работает, следите за одним: тесты должны появиться в diff'е **раньше**
реализации. Тесты, написанные после кода, проверяют то, что код делает, а не то,
что просила спека. Это подмена, которую легко не заметить в готовом diff'е.

### Шаг 3. Ревью

```
/review T4
```

Ревью идёт свежим контекстом — тот, кто наблюдал за написанием кода, наследует
его слепые пятна.

Что вы читаете в отчёте:

- [ ] каждый критерий приёмки помечен «есть тест» / «нет теста»;
- [ ] нет `unwrap()`, `expect()`, `panic!()` вне `#[cfg(test)]`;
- [ ] границы крейтов целы ([`architecture.md`](architecture.md) §2);
- [ ] в `Cargo.toml` не появилось зависимости без ADR;
- [ ] **не сделано ничего, чего спека не просила**. Лишняя фича — это провал
      ревью, а не бонус.

### Шаг 4. Снапшоты (только для T7–T12)

```bash
just snap
```

Смотрите каждый diff глазами и принимаете осознанно. `insta accept` вслепую
превращает снапшот-тесты в декорацию: они начинают фиксировать любой рендер,
включая сломанный.

### Шаг 5. Закрытие

Статус спеки в `Implemented` агент проставляет сам — это запись факта, а не
решение; вашей подписью служит мерж. Коммит и мерж он не делает.

```bash
git push -u origin HEAD
gh pr create               # тело PR: ссылка на спеку + критерии чеклистом
```

Мержите. Потом:

```
/clear
```

Обязательно. Иначе T5 потащит за собой весь контекст T4, и агент начнёт
опираться на детали, которых в спеке T5 нет.

После T9 Golden Path замыкается — продукт впервые работает целиком.

задачей вы читаете её спеку и переводите в `Approved` сами.

Спеки 005–008 доводятся до `Approved` **непосредственно перед своей задачей**, а
не пачкой заранее: UI-спека, написанная за четыре задачи до реализации, описывает
экран, чья модель состояния с тех пор изменилась. Устаревшая спека хуже
отсутствующей — её реализуют.

## 5. Когда что-то идёт не так

**Агент говорит, что архитектура неверна.** Это стоп-правило, и оно сработало
правильно. Он обязан остановиться и предложить ADR, а не перепроектировать на
ходу. Ваше действие: прочитать проблему, решить. Если решение — менять
архитектуру, то это отдельный ADR и отдельная задача, **не внутри текущего
diff'а**. Diff, где фича и архитектура меняются вместе, нельзя отревьюить.

**Агент добавил зависимость.** Зависимость — это архитектура. Нужен ADR. Без
ADR — убрать.

**Агент сделал больше, чем просила спека.** Убрать. Не «оставим, раз уж
написано»: спека — это определение готовности, а лишний код никто не заказывал и
никто не ревьюил.

**Агент предлагает что-то из списка отложенного** ([`roadmap.md`](roadmap.md)
§3) — async, relations, палитра команд, хуки, REST, FTS5. Это нарушение скоупа,
а не улучшение. Ответ — «M1» или «M2», список для того и существует.

**Задача не влезает в один PR.** Значит, её плохо декомпозировали. Разбивайте,
а не растягивайте PR.

## 6. Шпаргалка

```bash
just ci        # fmt --check + clippy -D warnings + test  ← перед каждым финишем
just test      # только тесты
just snap      # разбор снапшотов
just run       # открыть examples/blog в TUI
just validate  # проверить схему примера
```

```
/spec NNN описание    написать или доработать спеку
/task TN              реализовать задачу
/review TN            ревью diff'а по критериям
/clear                очистить контекст между задачами
```

## 7. Что дальше прямо сейчас

Настройка закончена. Осталось одно:

```
/task T1
```

T1 — единственная задача без спеки (скелет workspace), поэтому она стартует без
предварительного одобрения. Дальше на каждой задаче: `/spec` → читаете →
`Approved` → `/task` → `/review` → мерж → `/clear`.
