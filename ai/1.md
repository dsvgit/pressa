# Terminal CMS на Rust — Полный план

## 1. Идеи по улучшению и выбор технологий

### 1.1 Технологический стек

**TUI-фреймворк:**
- **ratatui** (форк tui-rs) — де-факто стандарт для TUI на Rust
- **crossterm** — кроссплатформенный backend для терминала (лучше чем termion)

**Архитектурный подход к UI:**
- **The Elm Architecture (TEA)** — Model-View-Update. Идеально ложится на TUI и упрощает работу AI-агентов (чистые функции, предсказуемость)
- Альтернатива: посмотреть на **tui-realm** (компонентный фреймворк поверх ratatui) — ускорит MVP, но добавит абстракций

**Данные и модель (главное для CMS):**
- Ключевая идея Payload — **schema-first / collections config**. Нужна декларативная схема.
- **serde** + **JSON Schema** или собственный DSL для описания коллекций
- Для MVP хранилище: **SQLite через sqlx** (compile-time проверенные запросы) или **rusqlite**
- Абстракция `Repository` trait → легко заменить бэкенд (SQLite → Postgres → REST API)

**Валидация:**
- **validator** crate + кастомные правила из схемы

**Асинхронность:**
- **tokio** — если планируешь работу с внешним API/AI. Для чисто локального SQLite можно и sync, но лучше сразу async.

### 1.2 Идеи улучшения концепции

| Идея | Зачем |
|------|-------|
| **Schema-driven UI** (как в discoveryjs/Payload) | Формы и таблицы генерируются из декларативной схемы, а не хардкодятся. Добавил поле в конфиг → UI сам обновился |
| **Command palette** (`:` или `Ctrl+P`) | Как в lazygit/vim — быстрый доступ ко всем действиям |
| **Access control hooks** | Payload-подобные хуки: `beforeChange`, `afterRead` — точки расширения |
| **Undo/redo стек** | Легко реализуется в TEA-архитектуре |
| **Экспорт/импорт (JSON/CSV)** | Полезно для локальной работы |
| **Query/filter bar** | Фильтрация записей как в discoveryjs |
| **Config через файл** (`cms.config.toml` / `.ron`) | Схема коллекций описывается вне кода |
| **Плагины через WASM (позже)** | Extensibility как у Payload |

### 1.3 Отличия/улучшения от исходного видения
- Разделить **domain layer** (схемы, репозитории) и **presentation layer** (TUI) — тогда можно будет сделать не только TUI, но и web/CLI фронтенды над одним ядром
- Keybindings вынести в конфиг (vim-like)
- Сделать **режимы** (Normal/Insert/Command) как в vim — естественно для терминала

### 2.3 Ключевые доменные типы

```rust
// cms-core/src/schema.rs
#[derive(Debug, Clone, Deserialize, Serialize)]
pub struct Collection {
    pub slug: String,
    pub label: String,
    pub fields: Vec<Field>,
    pub admin: AdminConfig, // какие поля в таблице
}

#[derive(Debug, Clone, Deserialize, Serialize)]
pub struct Field {
    pub name: String,
    pub label: String,
    pub field_type: FieldType,
    pub required: bool,
    pub validation: Option<ValidationRule>,
}

#[derive(Debug, Clone, Deserialize, Serialize)]
pub enum FieldType {
    Text,
    Number,
    Bool,
    Date,
    Select { options: Vec<String> },
    Relation { collection: String },
    RichText,
}
```

```rust
// cms-core/src/repository.rs
#[async_trait]
pub trait Repository: Send + Sync {
    async fn list(&self, collection: &str, query: &Query) -> Result<Vec<Record>>;
    async fn find(&self, collection: &str, id: &Id) -> Result<Option<Record>>;
    async fn create(&self, collection: &str, data: Record) -> Result<Record>;
    async fn update(&self, collection: &str, id: &Id, data: Record) -> Result<Record>;
    async fn delete(&self, collection: &str, id: &Id) -> Result<()>;
}
```

### 2.4 TEA-архитектура приложения

```rust
// cms-app/src/state.rs
pub struct AppState {
    pub collections: Vec<Collection>,
    pub screen: Screen,
    pub selected_collection: usize,
    pub mode: Mode,          // Normal | Insert | Command
    pub focus: Focus,        // Sidebar | Table | Form
    pub breadcrumbs: Vec<Crumb>,
    pub status: Option<StatusMsg>,
}

pub enum Screen {
    List { records: Vec<Record>, cursor: usize, query: Query },
    Edit { record: Record, field_cursor: usize, dirty: bool },
    Loading,
}

// cms-app/src/message.rs
pub enum Message {
    // Navigation
    FocusNext, SelectCollection(usize), EnterRecord(Id), GoBack,
    // Editing
    EnterInsertMode, InputChar(char), Backspace, FieldNext, FieldPrev,
    // Effects results
    RecordsLoaded(Vec<Record>), RecordSaved(Record), Error(String),
    // Commands
    Save, Delete, OpenCommandPalette, RunCommand(String),
    Quit,
}

// cms-app/src/update.rs
// Чистая функция: (State, Message) -> (State, Vec<Effect>)
pub fn update(state: &mut AppState, msg: Message) -> Vec<Effect> { /* ... */ }

// cms-app/src/effect.rs
pub enum Effect {
    LoadRecords { collection: String, query: Query },
    SaveRecord { collection: String, record: Record },
    DeleteRecord { collection: String, id: Id },
    AiSuggest { field: String, context: String },
}
```

**Event loop:**
```
crossterm event → Message → update() → (new State, Effects)
Effects исполняются async (репозиторий, AI) → возвращают Messages
render(State) → ratatui рисует
```

## 3. SDD + AI-агенты и Workflow

### 3.1 Spec-Driven Development структура

```
specs/
├── 00-overview.md            # видение, глоссарий, границы
├── 01-domain.spec.md         # доменная модель + инварианты
├── 02-repository.spec.md      # контракты Repository + примеры
├── 03-tea-app.spec.md         # Model/Message/Update таблица переходов
├── 04-tui.spec.md             # раскладка экранов, keybindings
├── 05-config-format.spec.md   # формат cms.config.ron
└── acceptance/
    └── mvp.feature            # Gherkin-сценарии для приёмки
```

**Формат спеки (пример фрагмента `01-domain.spec.md`):**
```markdown
## Field validation
GIVEN поле с `required: true`
WHEN значение пустое
THEN create/update возвращает ValidationError { field, "required" }
INVARIANT: Record не сохраняется если есть хоть одна ошибка

## Test contract
- test_required_field_rejects_empty()
- test_valid_record_saves()
```

Идея: **каждая спека → тесты → реализация**. Агент читает спеку, генерирует тесты, потом код.

### 3.2 Обвязка для AI-агентов

**Два уровня использования AI:**

**A. Dev-time (разработка кодовой базы) — главное для тебя сейчас**

Настрой инструменты, которые агент запускает сам:

```
xtask/ — CLI задачи (cargo xtask <cmd>)
  ├── check     → cargo fmt --check + clippy -D warnings + test
  ├── spec-test → запуск acceptance-тестов
  └── ci        → полный прогон
```

Правила для агента (`CLAUDE.md` / `.cursorrules` / `AGENTS.md`):
```markdown
# Agent rules
- Всегда сначала читай specs/ перед изменением crate
- TDD: сначала тест из спеки, потом код
- update() — только чистые функции, side-effects через Effect
- После изменений запускай `cargo xtask check`
- Domain layer НЕ зависит от ratatui/tokio
- Каждый PR обновляет соответствующую спеку
```

**Разбиение задач по агентам (специализация):**

| Агент | Зона ответственности | Контекст |
|-------|---------------------|----------|
| `domain-agent` | cms-core: схемы, валидация | 01-domain.spec |
| `storage-agent` | cms-storage: репозитории | 02-repository.spec |
| `app-agent` | cms-app: TEA логика | 03-tea-app.spec |
| `tui-agent` | cms-tui: views, рендер | 04-tui.spec |
| `reviewer-agent` | проверка соответствия спекам | все specs + tests |

**B. Runtime (AI внутри CMS — на будущее)**

```rust
// cms-agent/src/lib.rs
#[async_trait]
pub trait AiProvider {
    async fn suggest(&self, prompt: &str) -> Result<String>;
}
// Effect::AiSuggest — например автозаполнение полей,
```

### 3.3 Рекомендуемый workflow

```
1. SPEC     → пишешь/уточняешь спеку в specs/ (человек + AI ревью)
              ↓
2. DECOMPOSE → AI разбивает спеку на задачи + acceptance-критерии
              ↓
3. TEST      → агент генерирует failing-тесты из спеки (red)
              ↓
4. IMPLEMENT → агент реализует до green, гоняет `cargo xtask check`
              ↓
5. REVIEW    → reviewer-agent сверяет код со спекой + человек-ревью
              ↓
6. INTEGRATE → мердж, обновление спеки, следующая итерация
```

**Практические советы:**
- Начни с `cms-core` + `cms-storage` (memory) — самая изолированная и тестируемая часть, идеальна для отладки AI-workflow без TUI-шума
- TUI отлаживай снапшот-тестами: ratatui `TestBackend` + `insta` для snapshot буфера — агент сможет проверять рендер автоматически
- Держи domain-слой **без async и без ratatui** — это делает его быстро-тестируемым и понятным для агента
- Все Message/Effect enum'ы = «API» между слоями, документируй их в спеке

### 3.4 Стартовый порядок реализации MVP

```
Неделя 1: cms-core (schema, record, validation) + memory repo + тесты
Неделя 2: cms-app (TEA: state/message/update) + snapshot-тесты логики
Неделя 3: cms-tui (sidebar → table → form) + keybindings
Неделя 4: sqlite repo + config loader + polish + acceptance-тесты
```

## Итоговые ключевые решения
1. **ratatui + crossterm + TEA** — предсказуемый, тестируемый UI
2. **Schema-driven** ядро (как Payload) — UI генерируется из конфига
3. **Cargo workspace + Clean Architecture** — слои изолированы, легко для AI
4. **SDD**: спека → тесты → код → ревью, с специализированными агентами и `xtask` как «руки» агента
