# Terminal CMS на Rust

## 0. Краткое описание

Цель проекта — разработать локальную терминальную CMS на Rust.

Приложение должно быть похоже по концепции управления данными на [Payload CMS](https://github.com/payloadcms/payload), но работать локально в терминале. По интерфейсу можно вдохновляться `lazygit`, а по подходу к исследованию и построению интерфейсов данных — `discoveryjs`.

Основной сценарий:

- пользователь описывает сущности/коллекции через конфигурацию;
- запускает CMS локально в терминале;
- слева видит список сущностей;
- в центре видит таблицу записей выбранной сущности;
- может открыть запись;
- может редактировать поля;
- может создавать, обновлять и удалять записи;
- управление преимущественно с клавиатуры.

---

# 1. Видение продукта

## 1.1 Что должно получиться

Проект можно описать так:

```text
Payload CMS + lazygit + SQLite + Rust TUI
```

Это должна быть локальная schema-first CMS, где структура данных описывается декларативно, а терминальный интерфейс автоматически строится на основе этой схемы.

Пример запуска:

```bash
cms init
cms dev
```

После запуска пользователь видит terminal UI:

```text
┌──────────────────────────────────────────────────────────────┐
│ Home / Posts                                                │
├───────────────┬──────────────────────────────────────────────┤
│ Collections   │ title             status       updated       │
│               │──────────────────────────────────────────────│
│ > Posts       │ Hello world       draft        today         │
│   Users       │ About page        published    yesterday     │
│   Pages       │                                              │
│   Media       │                                              │
└───────────────┴──────────────────────────────────────────────┘
```

---

## 1.2 Цели MVP

MVP должен доказать, что можно:

- описывать collections через конфиг;
- запускать локальную CMS в терминале;
- просматривать записи;
- создавать записи;
- редактировать записи;
- удалять записи;
- валидировать данные по схеме;
- хранить данные в SQLite.

---

## 1.3 Что не является целью MVP

В MVP не нужно реализовывать:

- авторизацию;
- роли и permissions;
- Web UI;
- REST API;
- GraphQL API;
- полноценную систему плагинов;
- media library;
- rich text editor;
- сложные relationship-поля;
- сложные миграции схемы;
- multi-user режим;
- remote sync.

# 2. Основные идеи улучшения

## 2.1 Schema-first подход

CMS лучше строить вокруг схемы данных.

Пользователь описывает коллекции декларативно, а приложение на основе этой схемы строит:

- интерфейс;
- таблицу записей;
- форму редактирования;
- валидацию;
- CRUD-операции;
- базовые ограничения.

Пример `cms.yaml`:

```yaml
project:
  name: blog-cms

database:
  driver: sqlite
  path: cms.db

collections:
  posts:
    label: Posts
    fields:
      - name: title
        label: Title
        type: text
        required: true

      - name: slug
        label: Slug
        type: text
        required: true
        unique: true

      - name: status
        label: Status
        type: select
        required: true
        options:
          - draft
          - published

      - name: content
        label: Content
        type: textarea

      - name: views
        label: Views
        type: number

      - name: featured
        label: Featured
        type: boolean

  users:
    label: Users
    fields:
      - name: name
        label: Name
        type: text
        required: true

      - name: email
        label: Email
        type: text
        required: true
        unique: true
```

---

## 2.2 Разделение CMS core и UI

Даже если первая версия будет только терминальной, ядро CMS лучше отделить от интерфейса.

Рекомендуемое разделение:

```text
cms-core      — схемы, поля, валидация, доменные модели
cms-storage   — работа с SQLite/другими хранилищами
cms-app       — application services, use cases
cms-tui       — terminal UI на ratatui
cms-cli       — CLI-команды
```

Такой подход позволит в будущем добавить:

- Web UI;
- REST API;
- GraphQL API;
- headless-режим;
- плагины;
- хуки;
- миграции;
- импорт/экспорт;
- альтернативные хранилища.

---

## 2.3 SQLite как хранилище для MVP

Для первой версии лучше использовать SQLite.

Преимущества:

- не нужен отдельный сервер;
- отлично подходит для локального приложения;
- просто распространять;
- база хранится в одном файле;
- удобно делать демо и примеры;
- хорошо подходит для MVP.

Пример структуры пользовательского проекта:

```text
my-cms/
  cms.yaml
  cms.db
  media/
  migrations/
```

---

## 2.4 JSON records поверх SQLite

Для MVP не обязательно создавать отдельную SQL-таблицу под каждую коллекцию.

Можно хранить записи универсально:

```sql
CREATE TABLE records (
    id TEXT PRIMARY KEY,
    collection TEXT NOT NULL,
    data TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Где `data` — JSON:

```json
{
  "title": "Hello world",
  "slug": "hello-world",
  "status": "draft",
  "views": 100,
  "featured": true
}
```

### Плюсы

- проще реализация MVP;
- проще менять схемы;
- меньше проблем с миграциями;
- удобно для динамических коллекций;
- можно быстро добавлять новые field types.

### Минусы

- слабее типизация на уровне БД;
- сложнее делать индексы;
- сложнее обеспечивать уникальность полей;
- сложнее делать сложные запросы;
- хуже подходит для больших объемов данных.

Для MVP этот подход подходит хорошо.

В будущем можно добавить второй режим хранения:

```yaml
storage:
  mode: relational
```

- проще для embedded SQLite;

## 5.5 SchemaRegistry

`SchemaRegistry` хранит все коллекции и позволяет получать схемы по имени.

```rust
pub struct SchemaRegistry {
    collections: HashMap<String, CollectionSchema>,
}
```

Пример методов:

```rust
impl SchemaRegistry {
    pub fn get_collection(&self, name: &str) -> Option<&CollectionSchema> {
        self.collections.get(name)
    }

    pub fn require_collection(&self, name: &str) -> Result<&CollectionSchema, SchemaError> {
        self.collections
            .get(name)
            .ok_or_else(|| SchemaError::CollectionNotFound(name.to_string()))
    }
}
```

# 7. Application layer

Application layer реализует use cases и связывает `cms-core` со `cms-storage`.

## 7.1 RecordService

```rust
pub struct RecordService<R: RecordRepository> {
    repo: R,
    schema_registry: SchemaRegistry,
}
```

Пример методов:

```rust
impl<R: RecordRepository> RecordService<R> {
    pub fn list_records(&self, collection: &str) -> Result<Vec<Record>, AppError> {
        self.schema_registry.require_collection(collection)?;
        self.repo
            .list(collection, ListParams::default())
            .map_err(AppError::from)
    }

    pub fn create_record(
        &self,
        collection: &str,
        data: serde_json::Value,
    ) -> Result<Record, AppError> {
        let schema = self.schema_registry.require_collection(collection)?;
        validate_record(schema, &data)?;
        self.repo.create(collection, data).map_err(AppError::from)
    }

    pub fn update_record(
        &self,
        collection: &str,
        id: &str,
        data: serde_json::Value,
    ) -> Result<Record, AppError> {
        let schema = self.schema_registry.require_collection(collection)?;
        validate_record(schema, &data)?;
        self.repo.update(collection, id, data).map_err(AppError::from)
    }

    pub fn delete_record(
        &self,
        collection: &str,
        id: &str,
    ) -> Result<(), AppError> {
        self.schema_registry.require_collection(collection)?;
        self.repo.delete(collection, id).map_err(AppError::from)
    }
}
```

# 8. TUI architecture

## 8.1 Подход

Для TUI рекомендуется использовать модель:

```text
State + Event + Update + Render
```

Это похоже на Elm Architecture.

Главная идея:

- состояние приложения хранится явно;
- пользовательские события превращаются в actions;
- actions изменяют состояние;
- render строит UI из состояния.

---

```rust
pub struct TuiApp {

}
```

## 12.1 Пример ADR: SQLite

```md
# ADR-0002: Use SQLite for MVP

## Status

Accepted

## Context

The application should run locally without external services.

## Decision

Use SQLite as the embedded database for MVP.

## Consequences

Pros:

- No external dependencies.
- Easy local development.
- Portable project.

Cons:

- Limited concurrent access.
- Some schema migration complexity.
```

---

## 12.2 Пример ADR: JSON records

```md
# ADR-0003: Store records as JSON in SQLite

## Status

Accepted

## Context

Collections are dynamic and defined by user configuration. Generating relational tables for each collection would complicate MVP implementation and migrations.

## Decision

Store all records in a generic `records` table with JSON data.

## Consequences

Pros:

- Simple MVP implementation.
- Flexible schema evolution.
- Easy dynamic collections.

Cons:

- Weak database-level typing.
- More complex indexing.
- More complex unique constraints.
```

```md
# AGENTS.md

## Project

This is a Rust terminal-first CMS inspired by Payload CMS, lazygit and discoveryjs.

## Rules

- Follow specs in `/specs`.
- Do not introduce web server in MVP.
- Do not introduce async unless necessary.
- Keep core independent from TUI.
- Keep storage independent from TUI.
- Keep application layer independent from concrete UI.
- Prefer small modules and explicit types.
- All new behavior must have tests.
- Update specs when behavior changes.
- Do not add features outside MVP without explicit approval.

## Architecture

Crates:

- `cms-core`: domain model, schemas, validation.
- `cms-storage`: repository traits and SQLite implementation.
- `cms-app`: use cases.
- `cms-tui`: ratatui frontend.
- `cms-cli`: CLI entrypoint.

## MVP constraints

Allowed field types:

- text
- textarea
- number
- boolean
- select
- json

Not included:

- auth
- permissions
- web API
- GraphQL
- plugin system
- media library
- complex relationships
```

# 21. Итоговая рекомендуемая архитектура MVP

Рекомендуемый стек:

```text
Rust
Ratatui + Crossterm
SQLite via rusqlite
YAML schema via serde_yaml
JSON records via serde_json
Clean Architecture
Specification-Driven Development
AI agents through AGENTS.md + specs + ADR + CI
```

Главный принцип:

```text
schema -> validation -> CRUD -> TUI
```

Главное не пытаться сразу повторить весь Payload CMS.

Лучше сделать маленькое, но архитектурно чистое ядро:

- schema-first collections;
- базовая валидация;
- универсальное JSON-хранилище;
- terminal UI;
- CRUD;
- тесты;
- понятные specs.

После этого проект можно постепенно расширять без переписывания основы.
