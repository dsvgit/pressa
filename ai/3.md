# Rust TUI CMS: архитектура, стек и AI-workflow

Главная мысль: и Payload, и discoveryjs про одно и то же — UI, который генерируется
из декларативного описания данных, а не пишется руками под каждую сущность. Если
сразу заложить это как архитектурный принцип, MVP получится маленьким, но не
"одноразовым" — новые сущности будут добавляться конфигом, а не кодом.

---

## 1. Идеи по улучшению и стек

### Ключевой принцип: schema-driven UI

- Сущности (`Collection`) описываются как **данные** (YAML/RON/TOML), а не как
  Rust-структуры с ручным рендерингом.
- Есть один универсальный `TableView`, который умеет рисовать таблицу для *любой*
  коллекции, зная только её схему полей.
- Есть один универсальный `FormView`, который умеет рисовать форму ввода для
  *любой* коллекции.
- Каждый `FieldType` (text, number, bool, select, relation, date...) знает, как:
  - отрисовать себя в ячейке таблицы,
  - отрисовать себя как поле формы,
  - провалидировать введённое значение.

Это прямая аналогия с Payload (admin UI строится из `collections config`) и с
discoveryjs (view строится из декларативного view-model, а не хардкодится).

### UX-улучшения к твоей идее (в духе lazygit)

- **Контекстная подсказка снизу** — как в lazygit, строка с активными хоткеями
  меняется в зависимости от текущего экрана/панели.
- **Command bar по `:`** — быстрый переход к коллекции, поиск, действия
  (`:new`, `:delete`, `:goto users`).
- **Фильтр/поиск по `/`** внутри таблицы (fuzzy-match по видимым колонкам).
- **Relation-поля** — не просто ID, а поиск-пикер по связанной коллекции
  (список открывается оверлеем).
- **Панель "log"** снизу/сбоку — последние действия (создано/изменено/удалено),
  как git-лог в lazygit. Полезно и для отладки AI-агентами.
- **Global help `?`** — автогенерируемая из реестра хоткеев, а не захардкоженный
  текст.
- **Import/export** JSON/CSV — дёшево добавить, сильно повышает практическую
  ценность.
- **Headless core** — вынести домен и хранилище в отдельный крейт-библиотеку,
  чтобы потом (не в MVP) можно было навесить REST/веб-UI, не трогая бизнес-логику
  — ровно так же, как Payload headless.

### Технологический стек

| Слой | Выбор | Почему |
|---|---|---|
| TUI framework | **ratatui** + **crossterm** | Стандарт де-факто в Rust-экосистеме (gitui, bottom, zellij); огромное community; immediate-mode рендер отлично ложится на "рисуем таблицу/форму из схемы" |
| Текстовые инпуты | **tui-input** (однострочные), **tui-textarea** (многострочные) | Не изобретать курсор/выделение с нуля |
| Хранилище | **rusqlite** (sync, embedded SQLite) | Для локального CLI-инструмента синхронный код проще генерировать и тестировать агентам, чем async; SQLite = один файл, ноль внешних зависимостей |
| Миграции | **refinery** или самописный runner | Схема коллекций может проецироваться в таблицы SQLite |
| Конфиг схемы | **serde** + **serde_yaml** (или RON) | YAML читаемее для описания коллекций/полей |
| CLI | **clap** | Флаги: путь к конфигу, к БД, `--reset`, и т.п. |
| Ошибки | **thiserror** (доменные) + **anyhow** (в приложении) | Стандартная комбинация |
| Логирование | **tracing** + **tracing-appender** в файл | TUI занимает терминал — логи нужны только в файл, критично для отладки агентом |
| Тесты UI | **ratatui::TestBackend** + **insta** (snapshot) | Детерминированная проверка рендера без реального терминала — ключевая вещь для AI-агентов |
| Скриптинг (v2, не MVP) | **rhai** | Если позже захочется computed fields/hooks в духе Payload `beforeChange/afterRead` |

Альтернатива ratatui — **cursive** (более "widget-based", близко к готовым формам
из коробки). Но у ratatui сильно шире экосистема и она ближе к тому, что нужно для
схема-driven рендера (полный контроль над отрисовкой), поэтому лучше идти с ratatui.

## 2. Архитектура

### Слои (hexagonal / чистая архитектура)

┌─────────────────────────────────────────────┐
│  cms-tui (binary)                            │
│  Screens, Ratatui widgets, keymap, TEA loop  │
└───────────────────┬───────────────────────────┘
                     │ Action / Msg
┌───────────────────▼───────────────────────────┐
│  cms-core (lib)                                │
│  Collection, Field, FieldType, Record,         │
│  Schema, Validation, Repository trait          │
└───────────────────┬───────────────────────────┘
                     │ implements Repository
┌───────────────────▼───────────────────────────┐
│  cms-storage (lib)                             │
│  SqliteRepository (v1), JsonRepository (later),│
│  PostgresRepository (later)                    │
└─────────────────────────────────────────────────┘

Три крейта в одном workspace — `cms-core` не знает про ratatui и про SQLite,
только про trait `Repository`. Это даёт агентам чёткие границы: "меняешь домен —
не трогаешь UI" и наоборот.

### Домен (`cms-core`)

```rust
pub struct Schema {
    pub collections: Vec<Collection>,
}

pub struct Collection {
    pub slug: String,          // "posts"
    pub label: String,         // "Posts"
    pub fields: Vec<Field>,
    pub list_columns: Vec<String>, // какие поля видны в таблице
}

pub struct Field {
    pub name: String,
    pub label: String,
    pub kind: FieldType,
    pub required: bool,
}

pub enum FieldType {
    Text,
    Number,
    Bool,
    Select { options: Vec<String> },
    Relation { target_collection: String },
    Date,
}

pub struct Record {
    pub id: RecordId,
    pub values: serde_json::Map<String, serde_json::Value>,
}

pub trait Repository {
    fn list(&self, collection: &str) -> anyhow::Result<Vec<Record>>;
    fn get(&self, collection: &str, id: &RecordId) -> anyhow::Result<Record>;
    fn create(&self, collection: &str, values: RecordValues) -> anyhow::Result<Record>;
    fn update(&self, collection: &str, id: &RecordId, values: RecordValues) -> anyhow::Result<Record>;
    fn delete(&self, collection: &str, id: &RecordId) -> anyhow::Result<()>;
}
```

Валидация — метод `FieldType::validate(&self, value: &Value) -> Result<(), ValidationError>`,
вызывается и в форме (live), и перед `create/update` (source of truth).

### UI (`cms-tui`) — The Elm Architecture

Для ratatui-приложений почти стандарт — Model/Update/View, потому что:
- рендер становится **чистой функцией** от состояния → легко снэпшот-тестировать;
- вся логика переходов сосредоточена в одном `update()` → легко ревьюить/генерировать
  агентом маленькими диффами.

```rust
enum Screen {
    Sidebar,
    Table { collection: String, selected: usize },
    Form { collection: String, record: Option<RecordId>, draft: RecordValues, focus: usize },
    Help,
    ConfirmDelete { collection: String, id: RecordId },
}

struct AppState {
    schema: Schema,
    screen: Screen,
    breadcrumbs: Vec<String>,
    status_message: Option<String>,
}

enum Action {
    MoveDown, MoveUp, Select, Back,
    OpenRecord(RecordId), NewRecord, DeleteRecord(RecordId),
    SaveForm, EditField(usize), InputChar(char), Quit,
}

fn update(state: &mut AppState, repo: &dyn Repository, action: Action) { /* ... */ }
fn view(state: &AppState, frame: &mut Frame) { /* чистый рендер по schema */ }
```

Ключевая идея: `TableView`/`FormView` — не отдельные "экраны на коллекцию", а
generic-функции `fn render_table(collection: &Collection, records: &[Record], ...)`.
Одна и та же функция рисует и `posts`, и `users`, и любую будущую коллекцию.

Хоткеи — отдельный реестр
`Keymap { context: Screen, key: KeyEvent, action: Action, description: &str }`,
из него же генерируется bottom-hint-bar и `?`-хелп — не дублируется руками.

## 3. Обвязка для AI-агентов и SDD workflow

### Структура спеков

Заведи `/specs`, каждый файл — маленькая, независимо реализуемая фича, с
фиксированным шаблоном:

```markdown
# SPEC-0003: Table view for a single collection

## Context
...
## Goals / Non-goals
...
## Data model impact
...
## UI/UX flow
(ASCII-мокап экрана обязательно — агенту это заменяет скриншот)
## Acceptance criteria
- [ ] Given schema with collection "posts", table shows list_columns as headers
- [ ] Arrow keys move selection; Enter opens Form screen
## Test plan
- snapshot test on TestBackend for initial render
- snapshot test after pressing Down twice
```

Статусы: `Draft → Approved → In Progress → Implemented`. Это и есть SDD: агент не
пишет код, пока спека не Approved, и код должен закрывать именно Acceptance
criteria — ничего лишнего.

Архитектурные решения (стек, паттерн TEA, sync vs async и т.п.) — отдельно, в
`docs/adr/000X-title.md` (короткий ADR: контекст / решение / альтернативы /
последствия). Это не меняется каждую фичу, в отличие от `/specs`.

### Файл-инструкция для агента (`CLAUDE.md` / `AGENTS.md`)

Кладёшь в корень: конвенции кода (clippy strict, никаких `unwrap()` вне тестов),
структура крейтов, "не трогай `cms-core`, если спека про UI", ссылки на активные
ADR, команда для прогонки тестов перед коммитом.

Если используешь **Claude Code** — удобно завести под-агентов (`.claude/agents/`):
- **spec-writer** — превращает твой запрос в файл в `/specs` по шаблону, ничего
  не кодит;
- **architect** — при необходимости пишет ADR, декомпозирует спеку на шаги;
- **implementer** — реализует один шаг спеки, пишет тесты;
- **reviewer** — гоняет `cargo clippy`, `cargo test`, сверяет диф с acceptance
  criteria спеки.

Плюс кастомные slash-команды типа `/spec`, `/implement-spec 0003`, `/adr`.

### Почему тесты критичны именно для AI-агентов в TUI

Обычный TUI нельзя "посмотреть глазами" в CI, но у ratatui есть `TestBackend` —
рендер в буфер, который можно ассертить как текст:

```rust
let backend = TestBackend::new(80, 24);
let mut terminal = Terminal::new(backend)?;
terminal.draw(|f| view(&state, f))?;
insta::assert_snapshot!(terminal.backend().buffer());
```

Это даёт агенту **детерминированный сигнал успеха/провала** без человека — именно
то, что нужно для автономного цикла "написал код → прогнал тест → увидел диф
буфера → поправил". Обязательно закладывай это с первой же спеки, не откладывай
"на потом".

### Дорожная карта MVP (порядок спеков)

1. Скелет workspace, `cms-core` с `Schema`/`Repository` trait, конфиг из YAML с
   одной тестовой коллекцией.
2. `SqliteRepository`: create/list/get работают на этой коллекции.
3. Экран Sidebar + Table (read-only) для одной коллекции, TestBackend-снэпшоты.
4. Экран Form: создание записи, базовая валидация required-полей.
5. Редактирование существующей записи + удаление с confirm-диалогом.
6. Несколько коллекций одновременно + breadcrumbs + relation-поле как
   поиск-пикер.
7. Help-оверлей, bottom hint bar, `:` command bar, `/` фильтр в таблице.

Каждый пункт = 1 spec-файл = 1 relatively self-contained PR, который агент может
закрыть и который легко ревьюить человеку.
